# Measured Pilot 吞吐优先预检与正式运行计划

## Summary

基于当前证据，根因不是“GPU 没分到”，而是现有 `full_gpu` 路径走 `transformers` 的 `device_map=auto`，配合 `PROFILE_CHUNK_SIZE=10`、`max_new_tokens=16`、单 worker 串行批次，导致显存长期驻留但 GPU 计算利用率很低；同时残留进程占卡会放大 OOM 风险。下一轮保持 `2026-08-01` 至 `2026-08-15` 阶段边界不变，不切真实 `vLLM/LMCache` backend，只优化当前 measured pilot 主链的吞吐与 GPU 利用率。

计划采用“两步走”：

1. 先做吞吐预检轮，目标是验证清理、绑卡、chunk/batch 调整能显著抬高 GPU 利用率且不破坏 measured 接口。
2. 通过预检后，再进入正式 `configs/pilot.yaml` 运行。

## Key Changes

### 1. 进程与设备清理策略

- 在下一轮开始前，显式终止当前残留的实验相关进程：`run_experiment.py`、其 `conda run` 包装进程、`profiles.transformers_runtime` 子进程。
- 清理后立即做一次 `nvidia-smi` 快照，确认 3 张 2080 Ti 上无遗留 Python 进程、显存基本回落到空闲态，再允许新一轮启动。
- 新一轮执行统一写入独立时间戳日志和 pid 文件，避免沿用旧 `out/logs/pilot_measured.pid` 指针造成误判。
- 若下一轮仍出现多张卡被单进程低利用率占满，则直接判定为“运行路径问题”而不是“环境偶发波动”。

### 2. measured pilot 吞吐优先改造

- 保持算法、baseline、measured profile 表与 `run_experiment.py pilot-smoke-measured` 主入口不变，不改论文阶段边界。
- 优先把 `full_gpu` 的 runtime 从通用 `transformers_runtime` 迁移到已有的 Qwen2 专用 runtime 路径，使其与 KIVI/H2O 一样走更明确的设备映射与 batch 逻辑，而不是 `device_map=auto`。
- 为 profile 构建链路引入显式运行时参数，至少包括：
  - `profile_chunk_size`
  - `cuda_visible_devices` 或按 adapter/backend 区分的设备绑定
  - `device_mode` / `device_map_strategy`
- 默认策略定为：
  - `full_gpu`、`kivi_*`、`h2o_*` 均固定在单张空闲卡上运行，禁止自动跨 3 卡铺开。
  - 预检轮先单卡打满，再考虑是否需要多卡并行 profile adapter 级别扩展。
- `PROFILE_CHUNK_SIZE` 不再硬编码为 10；改成配置驱动，预检轮用更大的 chunk 做吞吐探测。
- `max_new_tokens` 在吞吐预检轮允许上调，用于把 GPU 从“极短 decode、频繁调度”改成更连续的计算负载；正式 pilot 是否回落由预检结论决定。
- 保持输出 schema 和 summary 字段兼容，不能破坏 H0/H1/H2-lite 现有统计口径。

### 3. 吞吐预检轮设计

- 新增或约定一份吞吐预检配置，仍基于 measured pilot 主链，但规模受控：
  - 请求量小于正式 `pilot.yaml`
  - 输出 token 长度高于正式配置
  - chunk size 大于当前默认值
  - 固定单卡绑定
- 预检轮目标不是论文结论，而是验证运行形态：
  - GPU 利用率显著高于当前接近 0 的状态
  - 不再出现“3 卡同时占显存但几乎无计算”的模式
  - `full_gpu`、`kivi`、`h2o` 都能完整返回 measured rows
  - 不发生 OOM
- 预检轮完成后再决定正式 `pilot.yaml` 的保守参数：
  - 若更大 chunk 与更长 decode 明显提升利用率且无 OOM，则把其中安全的参数回迁到正式 pilot。
  - 若吞吐提升依赖过长 decode、会改变论文 measured 条件，则仅保留设备绑定和 runtime 路径优化，不保留 workload 放大参数。

### 4. 正式 pilot 准入条件

- 只有在以下条件全部满足后，才启动正式 `configs/pilot.yaml`：
  - 清卡后 GPU 空闲状态确认通过
  - 吞吐预检轮无 OOM
  - `full_gpu` 不再走低效的跨卡 `device_map=auto` 模式
  - profile 构建过程中 GPU 利用率有持续非零区段，且日志可定位各 chunk 完成进度
  - 输出 profile CSV、failed chunk sidecar、summary CSV 仍符合当前接口
- 正式 pilot 运行时沿用同样的进程管理、日志命名和设备绑定策略。
- 若正式 pilot 仍失败，优先保留失败现场与 GPU 快照，不立即继续加大参数；先回到预检配置复现。

## Test Plan

- 进程清理验证：
  - 清理前后分别采集 `ps` 与 `nvidia-smi`，确认目标进程消失、显存释放。
- 吞吐预检验证：
  - 运行预检配置一轮，记录 GPU 利用率、显存、chunk 完成日志、总耗时。
  - 对比当前基线现象：从“多卡占显存但 0 到 12% 利用率”改善为“单卡或受控设备上持续有计算利用率”。
- 兼容性验证：
  - 检查预检输出仍能生成 profile table、summary、failed chunk sidecar。
  - 确认 H0/H1/H2-lite 依赖字段未缺失。
- 正式运行前验证：
  - 用与正式 pilot 相同入口做一次小规模 smoke，确认设备绑定、chunk 参数、runtime 路径都按预期生效。
- 正式 pilot 验证：
  - 启动 `configs/pilot.yaml` 后只接受两类结果：完整成功，或带完整失败证据的可诊断失败；不接受只有 `conda run failed` 包装层单行日志的不可诊断失败。

- 预检轮允许使用比正式 pilot 更激进的 chunk 与 decode 参数做运行形态验证；正式 pilot 只吸收其中对论文条件无害的优化。
