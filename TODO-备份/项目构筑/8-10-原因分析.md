  根因定位

  1. 配置选错数据路径

     configs/pilot.yaml:43 使用：

     requests: data/fixtures/pilot_qa_summary_requests.jsonl

     该 fixture 是扁平 QA/摘要请求，没有 session_id 和多 turn。相反，configs/
     pilot_session_trace.yaml:43 才使用 pilot_session_trace_requests.jsonl，并配
     置了 session trace 预算。

     run_util/data_utils.py:67 会直接保留空的 session_id，不会为普通 JSONL 请求自
     动补 session。

  2. MeasuredReplayBackend 因空 session 直接绕过状态模拟

     backends/measured_replay.py:115：

     if not request.session_id:
         return baseline

     因此本次结果没有进入 CacheState、全局预算、session resident、evict、restore/
     recompute 逻辑。backend 不是没写，而是本次输入没有触发它。

  3. Policy 的预算判断退化成单请求 profile 内存判断

     policies/base.py:170 在无 session 时只返回 profile 的静态统计内存：

     if request is None or cache_state is None or not request.session_id:
         return self._memory_or_inf(profile)

     所以 4900/5000 MiB 都远大于单请求 KV 的约 7~72 MiB，不会产生 policy budget
     filter，也不会产生 backend budget hit。

  4. 当前 runner/backend 接口仍是 Pilot 收缩版

     run_util/run_policies.py:192 是“逐请求决定一个 profile，再调用 backend”，而
     不是 README 所描述的动作级、多对象执行框架。这个结果正好验证了 README-当前实
     现对照.md:58 的判断：当前实现仍是“单请求、单动作、轻量 STC”。


---

这次 out/20260810_093019_pilot 没满足理想 baseline_smoke 表要求，已经可以落实到4 个具体的设计/代码问题，不再只是“实验现象”。

  1. 实验轨道用错了目标口径

     这次运行的是 baseline_quality，不是 baseline_session。configs/pilot.yaml:5
     明确写的是 experiment.type: baseline_quality，请求文件也是独立质量请求
     pilot_qa_summary_requests.jsonl，configs/pilot.yaml:46；而双轨计划明确规定这
     条轨“只用于 5 条 baseline 的质量、TTFT 和 KV 分化，不宣称 backend/session 事
     件语义”：2026-08-10-baseline-smoke-dual-track-plan.md:7。因此 summary 里
     backend_events_applicable=False、backend_semantics_status=not_applicable 是
     符合当前代码设计的，不是偶发失败：out/20260810_093019_pilot/policy_tables/
     pilot_smoke_measured_total_summary.csv:2。

     这意味着：如果拿这次结果去对照 理想baseline_smoke表说明.md:18 里包含
     session/backend 事件链的要求，必然不达标。这里首先是设计口径不一致，不是实现
     细节先坏掉。

  2. memory_budget_mib 在质量轨上基本是失效设计

     根因在 policies/base.py:170。_projected_memory() 对没有 session_id 的请求直
     接退化为单 profile 的 p95_kv_cache_memory_mib。当前质量轨请求确实没有
     session 链，out/20260810_093019_pilot/profile_tables/
     pilot_smoke_measured_profiles.csv:2 里这些请求的 session_id 为空。结果就是策
     略预算判断比较的不是“全局/会话驻留内存”，而只是单请求 profile 的 KV 占用。

     但当前 profile 的 p95_kv_cache_memory_mib 量级只有十几到几十 MiB，而 sweep
     预算是 4900/5000 MiB。configs/pilot.yaml:41 所以所有 lossy profile 都天然“在
     预算内”，预算过滤不会触发，4900 和 5000 两档自然整行重复：
     out/20260810_093019_pilot/policy_tables/
     pilot_smoke_measured_total_summary.csv:2、out/20260810_093019_pilot/
     policy_tables/pilot_smoke_measured_total_summary.csv:7。

     这不是参数刚好没打中，而是质量轨预算语义和策略预算实现的量纲不匹配。在当前设
     计下，质量轨上的 memory_budget_mib 几乎不可能产生理想说明要求的预算响应。

  3. utility_dynamic 的打分公式设计导致它坍缩成 static_best

     这已经可以落到具体代码：policies/utility_dynamic.py:28。它的分数是：

     score = p95_ttft + 0.05 * memory + 1000 * pred_loss

     这里有两个关键设计后果。

     第一，memory_weight=0.05 太小。当前 profile 之间 KV 差异约 10 MiB 级别，只贡
     献不到 1 ms 的分数差；pred_loss 差异约 0.001 级别，只贡献 1 ms 左右；真正主
     导分数的是几十毫秒量级的 p95_ttft_ms。所以这个“utility”并没有把内存收益拉到
     足够强，实际上几乎就是“选 TTFT 最好的可接受 profile”。

     第二，它用的是全局 profile 级 p95 TTFT 加 bucket 平均 predicted loss，不是
     request-specific 的真实 utility。于是对所有 task/length bucket，它都被同一个
     profile 吸过去。按校准子集复算后，utility_dynamic 在 qa/nonshort、qa/short、
     summary/nonshort、summary/short 四个组里，最优分数全都是
     kivi_4bit_residual64。这正好解释了结果里它和 static_best 完全重合：
     out/20260810_093019_pilot/policy_tables/
     pilot_smoke_measured_total_summary.csv:3、out/20260810_093019_pilot/
     policy_tables/pilot_smoke_measured_total_summary.csv:5。

     所以这里不是“实验偶然把两条线跑成一样”，而是**utility_dynamic 当前实现从设计
     上就不足以形成理想说明里的激进低内存线**。

  4. static_best / static_safe 的静态选型设计，使 epsilon/delta 敏感性过弱

     这两个策略的核心都在 policies/base.py:205。_best_profile() 先在校准集上算每
     个 profile 的整体统计，然后固定选一个 profile；static_best 只要求 mean_loss
     <= epsilon，static_safe 额外要求 violation_rate <= delta：policies/
     static_best.py:19、policies/static_safe.py:19。

     但在这次校准子集上，绝大多数 lossy profile 本来就已经同时满足这些约束；而一
     旦进入候选集，最终又几乎只按 p95_ttft_ms 排序。因此 4 组 (epsilon, delta)
     下，static_best 都固定选 kivi_4bit_residual64，static_safe 也大多选它，只有
     线上逐请求 guard 把一部分请求回退 exact，才让表面动作分布有些差异。

     这说明当前问题不是“阈值没调好”，而是静态 profile baseline 的设计本身太容易坍
     缩到同一个最快 profile，无法自然产生理想说明里希望看到的“static_best、
     static_safe、utility_dynamic 三条线明显分离”的结构：理想baseline_smoke表说
     明.md:47、理想baseline_smoke表说明.md:190。

  归总成一句话

  这次不达标的最终根因是：

  - 用 baseline_quality 轨去对照含 backend 语义的理想口径，这是实验设计口径问题。
  - 在 baseline_quality 内部，memory_budget_mib 与无 session 的单请求 KV 估计比
    较，导致预算 sweep 失效，这是预算语义设计问题。

  - utility_dynamic 的分数几乎被 p95_ttft 主导，天然收敛到和 static_best 一样的
    profile，这是控制器目标函数设计问题。

  - static_best/static_safe 用校准集整体统计固定选 profile，epsilon/delta 只做弱
    过滤，不足以形成稳定分化，这是baseline 族设计问题。
