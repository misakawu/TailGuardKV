## 1. 这轮实验实际上测到了什么

本轮结果包含 80 行策略汇总，参数覆盖：

- 预算：3400、3900、4400、4900 MiB
- (\varepsilon)：0.05、0.1
- (\delta)：0.05、0.1
- 策略：full_lru、static_best、static_safe、uncalibrated_dynamic、utility_dynamic

但 0.7 要求同时实现并比较的 tailguard 和 quality_oracle 没有出现在本轮策略列表中。也就
是说，这次运行更接近 baseline 粗扫，还不是“一体化预实验”的完整执行。

四档预算下，策略结果没有变化。以已有输出为例：

- utility_dynamic 的 p95 TTFT 始终为 1333.51 ms，p95 KV cache 只有 21.45 MiB。
- uncalibrated_dynamic 的 p95 TTFT 始终为 1370.13 ms，p95 KV cache 为 32.94 MiB。
- 两者的质量损失、违例率、fallback 和动作比例也都不随预算变化。

最低预算已经是 3400 MiB，而实际 p95 KV cache 仍处在几十 MiB 的量级。这个预算区间没有给
策略造成内存压力，所以四档预算名义上不同，实际是同一个运行条件。

这恰好对应规划文档中的后期注释：如果 global_resident_kv_mib 长期碰不到预算线，就不会发
生 budget hit、evict、restore 或 recompute，最后测到的只是静态 profile 差异，而不是显
存受限控制问题。

## 2. 对 H0、H1、H2-lite 的判断

### H0 Tail-risk：当前没有验证

H0 要求至少在两类任务中观察到这样的现象：不同 profile 的平均损失接近，但 q95、q99 损失
或违例率相差至少 2 倍。

本轮已展示的动态策略结果中：

mean_quality_loss = 0
p95_quality_loss = 0
p99_quality_loss = 0
cvar_quality_loss = 0
violation_rate = 0

这些结果没有尾部差异，无法支持“平均质量掩盖尾部灾难”的假设。但这还不能算 H0 失败，因为
当前证据没有确认：

1. 是否覆盖了规划要求的两类任务；
2. 不同 profile 是否产生了足够多的质量差异；
3. 质量标签是否真实区分了对压缩敏感和不敏感的请求；
4. H0 是否按 profile 单独统计，而不是只看策略选择后的聚合结果。

因此，H0 的准确状态是：尚未被有效检验。如果在补齐任务与 profile 对照后，质量损失仍全部
为零，才需要怀疑数据集、质量度量或 profile 强度不足。

### H1 Calibration：数值达标，但属于空检验

规划要求在 (\delta=5%) 时，ID 违例率不高于 7%，分组违例率不高于 8%，同时不能靠全部选择
full profile 获得表面安全。Pilot 的统一标准稍微宽松一些，要求 empirical violation 不高
于 8%，exact fallback ratio 小于 60%。

当前结果中，已展示策略的：

violation_rate = 0
worst_group_violation = 0
safe_ratio = 1
exact_fallback_ratio = 0

从数值上看，这些指标通过了门槛，而且不是“全部 full”的空保证。问题是，质量损失也全部为
零。如果所有候选 profile 本来就不会产生违例，那么校准器无需识别风险，点预测和校准 UCB
都能轻易得到零违例。

更重要的是，真正需要验证 calibration 的 tailguard 没有出现在本轮策略列表中，target-vs-
empirical coverage 和 UCB 相关证据也没有完整反映在当前摘要里。

所以 H1 不能写成“已经通过”。更准确的判断是：

> 当前数据没有发现违例，但也没有形成足以检验校准能力的风险样本。H1 仍待验证。

### H2-lite：当前 cell 无效，不能比较收益

H2-lite 要求在 1 模型、2 任务、2 预算的设置中，至少两个有效 cell 相比最佳可部署
baseline 达到以下任一收益：

- p95 TTFT 降低至少 10%；
- 显存降低至少 15%；

同时质量违例必须达标。

本轮所有预算下的结果相同，说明这些预算不是有效 cell。有效预算必须迫使策略做出不同选
择，至少应出现下面一种变化：

profile 选择变化
budget hit
evict
restore
recompute
exact fallback
global resident 接近预算

本轮摘要中的 budget_hit_rate、restore_count、recompute_count、
mean_global_resident_kv_mib 和 p95_global_resident_kv_mib 都是空值，无法证明发生过预算
竞争。规划要求输出的 controller、QRP、CG 和 STC 开销同样为空。

因此，这 4 档预算不能作为 4 个有效 cell 计入 H2-lite。当前也缺少 tailguard 结果，无法
计算它相对最佳 baseline 的收益。

H2-lite 的状态是：未执行到能够判定通过或失败的阶段。

## 4. 完整实验是否可行

### 工程可行性：较高

现有框架已经能完成 baseline 网格运行，并按 policy、预算、(\varepsilon) 和 (\delta) 输
出质量、TTFT、显存与动作指标。参数组合也确实进入了最终汇总。这说明基础实验流水线可以扩
展，不需要推倒重来。

不过，规划要求的完整一体化实验还缺三块：

1. 把 tailguard 和 quality_oracle 放进同一批结果；
2. 让全局驻留、budget hit、迁移和控制器开销真正进入汇总；
3. 用真实的紧预算和并发 trace 触发策略决策。

这些属于补齐实验闭环，不是架构方向错误。

### 实验设计可行性：有条件可行

当前最大问题不是模型收益太小，而是实验条件没有制造出需要控制器解决的问题。

规划研究的是显存受限条件下的动态 KV 管理。若预算是 3400 MiB，而策略的 p95 KV cache 只
有 20 至 35 MiB，控制器根本不需要在质量、TTFT 和显存之间取舍。此时比较动态算法，容易得
到所有预算结果相同的结论。

下一轮应先找出预算发生相变的区间，再做完整矩阵。预算点应围绕实际全局 resident 峰值设
置，而不是继续从 3400 MiB 机械下降 500 MiB。

可采用两阶段方式：

1. 先用少量请求做紧预算定位，找出首次 budget hit、首次 profile 切换和首次 fallback 所
    在区间。

2. 再围绕这些阈值设置高、中、低三档预算，执行每个 cell 至少三次的正式 Pilot。

规划本身也规定系统回放每个 cell 至少重复三次，并要求在回放中真实累积并发请求的驻留压
力。

### 论文假设可行性：暂时无法判断

现在既没有证据证明 H0 成立，也没有证据表明 H0 不成立。H1 和 H2-lite 同样没有进入有效检
验条件。

这意味着完整实验目前处于“可继续，但必须先修正 Pilot”的状态。不能直接扩大到更多模型和任
务，否则只会把当前无效预算复制到更大的矩阵中，消耗大量算力，却仍回答不了论文问题。

## 5. 当前阶段的下一轮最小验证

当前进度仅到 **2026-08-01 至 2026-08-15**：统一 `Policy`、`Backend`、`Metric` 接口，实现 5 个 baseline，并形成 `run_experiment.py` 与 baseline smoke 表。因此，下一轮只验证当前阶段已有能力，不安排 2026-08-15 之后的任务。

### 第一步：重新定位预算

在现有 5 个 baseline 和现有运行入口内调整预算区间，使至少部分 cell 能产生有效资源压力。预算值应依据当前可用的 KV memory 或 resident 指标逐步收窄。

### 第二步：验证预算是否��生效

检查不同预算下 profile、`budget_hit_rate`、缓存事件、内存指标和 TTFT 是否发生变化。如果低预算下仍完全没有变化，应优先检查预算传递、resident 统计及指标聚合链路。

### 第三步：复查统一输出

确认 5 个 baseline 均能通过 `run_experiment.py` 运行，并进入字段一致的 baseline smoke 表。当前阶段只验证接口兼容、运行链路和聚合结果，不承担完整实验或论文假设验证任务。

## 最终��结论

本轮结果表明，截止 2026-08-15 已完成的统一接口、5 个 baseline、`run_experiment.py` 和 baseline smoke 聚合链路具备基础可用性。

当前预算尚未形成足够的资源压力，因此本轮只能证明 baseline 网格可以运行和汇总，不能据此比较 5 个 baseline 在资源受限条件下的效果。下一步应限定在当前阶段内，重新定位有效预算，并验证预算事件和已有指标能够正确记录与聚合。

本文不把 2026-08-15 之后的策略扩展、完整 Pilot、论文假设验证、任务扩展、多轮重复或真实后端工作列为本轮缺陷或立即行动项。
