## 3. 5 条 baseline 尚未形成可解释的差异曲线

理想说明特别强调不能让 5 条 baseline 全挤在一起。当前结果中确实已经出现不同 profile，例如：

- full_gpu
- kivi_4bit_residual32

而且运行数据中两者的 TTFT 已经出现明显差异，示例结果中 full_gpu 请求约为 100 到 115 ms，而 kivi_4bit_residual32 的示例
请求约为 39,771 ms。

但这个差异目前不能直接当成理想的 baseline 曲线，因为：

- 它只展示了局部请求；
- 尚未证明五种方法全部齐全；
- 尚未证明每种方法使用相同请求集合；
- 尚未证明质量口径一致；
- 尚未证明几万毫秒的差异来自方法本身，而不是 worker 切换、模型装载、冷启动或 fallback。

### 具体代码设计原因

在 <File>backends/qwen_session.py</File> 中，运行时按 profile family 管理 worker；切换或释放 runtime 时，会向 worker
发送 cache-control 请求，并生成 profile_runtime_released 类型的 eviction 事件。

这意味着当前 measured latency 可能同时包含：

- KV 策略代价；
- profile 对应 worker 的运行差异；
- runtime/profile 切换代价；
- cache-control 通信代价；
- 冷启动或首次执行代价。

如果聚合器只按 policy/profile 求 TTFT 分位数，而没有对 warm-up、worker 生命周期和 runtime switch 做独立标记，那么最
终“曲线拉开”可能是基础设施噪声，而不是 baseline 策略差异。

## 4. baseline_quality 的“不适用”语义尚未落实为单独 schema

理想说明要求：质量表中的 session/backend 字段应为空值或 N/A，不能把 0 当成“没有采集”。

当前输出仍采用通用 summary 结构，其中大量字段同时服务于质量、策略、风险、backend 和 session。示例行中可以看到多项事件
类字段出现 0.0，同时质量风险状态为 risk_evidence_insufficient。

问题在于，0.0 至少可能代表三种不同情况：

1. 确实采集了，事件没有发生；
2. 当前 backend 不支持该指标；
3. 当前表根本不应包含该指标。

这三种状态在统计上不能等价。

### 具体代码设计原因

根因在通用 summary 模型：同一个 row schema 同时承载 quality 和 session 指标。聚合时，数值字段通常需要一个默认值，缺失
值因此很容易被转换成 0，再参与均值或求和。

正确设计应保留三态：

None / 空值：不适用或未采集
0：已采集，事件未发生
>0：已采集，事件发生

如果需要进一步区分“未采集”和“不适用”，还应增加：

metric_status = measured | not_applicable | unavailable

———

## 5. session 事件链已经有状态模型，但“budget hit”的解释不够单一

当前两套 backend 都产生 budget_hit 和 global_resident_kv_mib：

<File>backends/measured_replay.py</File> 从 fixture 中读取 baseline.budget_hit，并可能在 replay 过程中再次把它设为
true；

<File>backends/qwen_session.py</File> 使用 bool(budget_victims) 推导 budget hit；
- Qwen session 还根据 global resident 与 global budget 的关系处理受害 session。

这造成 budget_hit 的来源并不完全一致：

measured replay:
fixture 声明 + replay 二次推导

online qwen:
是否产生 budget victims

因此，相同的 budget_hit=True 在两个 backend 中可能表示不同事件：

- 预计会超预算；
- 实际产生了 victim；
- 发生了降级；
- 发生了 eviction；
- fixture 原始记录就是 true。

### 具体代码实现位置

在 <File>backends/measured_replay.py</File>：

- 先保存 previous_global；
- 从 baseline.budget_hit 初始化；
- 计算 projected_global；
- 可能执行 session 释放；
- 最后写入新的 global_resident_kv_mib 和 budget_hit。

在 <File>backends/qwen_session.py</File>：

- budget_hit = bool(budget_victims)；
- 更新 session/global resident；
- 超过 _global_budget_mib 时继续处理 victim；
- _drop_session() 将 victim resident 设为 0，并从 global resident 中扣除对应 KV。

状态更新本身已经比较完整，但汇总表如果只有一个布尔字段，就无法解释是哪一种 budget 事件触发。因此理想表要求的“事件链自
洽”尚未完全满足。

建议至少拆成：

budget_pressure_detected
budget_victim_selected
budget_eviction_executed
budget_fallback_executed
budget_resolution

## 6. eviction 的统计可能混入 runtime/profile 切换释放

在 <File>backends/qwen_session.py</File> 中，runtime 释放会生成：

event_kind = "evict"
event_reason = "profile_runtime_released"
budget_resolution = "runtime_switch"

这在事件日志层面是可解释的，但如果 summary 只统计 event_kind == "evict"，就会把两类不同事件混在一起：

1. 内存预算压力导致的 cache eviction；
2. profile/runtime 切换导致的主动释放。

这会破坏理想表中的逻辑关系：

budget hit -> victim -> eviction -> restore/recompute

因为 runtime switch eviction 并不一定由 budget hit 引起。

### 代码设计根因

底层事件已经有 event_reason 和 budget_resolution，说明 backend 层保存了区分信息；真正的问题更可能位于 summary 聚合层，
聚合时如果只按事件种类计数，而不按 reason/resolution 分类，就会丢失因果信息。

因此正式表至少应该分别输出：

budget_eviction_count
runtime_switch_release_count
policy_eviction_count

而不是只有笼统的 eviction_count。

———

## 7. global_resident 的状态更新可追踪，但尚缺少聚合级不变量检查

当前代码已经显式维护 global resident：

- measured replay 根据 previous resident、当前 resident 和其他 session 状态计算 projected/global resident；
- Qwen session 使用 old_global - previous_resident + resident_after 更新；
- _drop_session() 使用 max(0.0, global - kv_mib) 扣减。

但使用 max(0.0, ...) 也会掩盖一种错误：如果状态账本重复扣减或 victim KV 大于账面 global resident，结果会被静默截成 0，
而不是暴露账本不一致。

理想表要求事件链自洽，因此需要在聚合或测试层增加不变量：

global_after
= global_before
- released_or_evicted
- previous_session_resident
+ new_session_resident

并验证：

global_resident >= 0
global_resident ≈ 所有 session resident 之和
budget eviction 后 global_resident <= budget
被 drop 的 session resident == 0
eviction 后再次访问必须出现 restore 或 recompute

当前工具结果能确认状态更新代码存在，但不能确认这些跨请求不变量已经在最终聚合流程中全面执行。

# 二、按严重性排列的根因判断

## P0：输出数据契约仍是 diagnostic summary，而非正式 baseline schema

这是最根本的问题。只要质量和 session 仍共用一个通用 summary，后续就会持续出现：

- N/A 被写成 0；
- quality 与 backend 指标混表；
- 事件计数失去原因；
- 单批次结果被误认为最终表；
- 五条 baseline 的完整性无法自动验证。

## P0：缺少统一的实验矩阵完整性检查

最终聚合器应该在输出前强制验证：

expected baselines == observed baselines
expected batches == observed batches
expected configs == observed configs
request-id sets identical across baselines
duplicate request-id count == 0
failed chunk count == 0

当前存在 failed-chunks 表，说明运行框架已经记录失败分片，但现有 final aggregation 目录仍没有展示一个明确的“整体可用性
结论”。

## P1：聚合层可能丢失事件原因

底层事件包含 event_reason 和 budget_resolution，但正式 summary 如果只保留 eviction_count、budget_hit_rate，就无法证明
事件链闭合。

## P1：backend 间 budget_hit 定义不统一

online Qwen 用 victim 推导，measured replay 又继承 fixture 值。两个 backend 的同名字段必须先规范语义，否则横向比较不可
靠。

## P1：profile/runtime 生命周期污染 baseline latency

如果不同 profile 触发不同 worker 生命周期，TTFT 差异不能直接解释成 KV 策略差异。应单独标记：

cold_start
worker_restart
profile_switch
runtime_release
cache_control_latency

然后正式 baseline 曲线至少应提供 warm-only 和 all-request 两种口径。

## P2：账本通过 max(0.0, ...) 静默吞掉负值

这有利于运行不中断，但不利于发现 resident 重复扣减。baseline 验证阶段应先 assert，再在生产路径进行保护性截断。

# 四、后续修改建议

本次实验的主要用途不是直接生成正式 baseline 表，而是寻找能够真正触发 profile 选择的紧预算区间。因此，后续工作应优先围绕预算扫描和 profile 选择链路展开，不必先按正式 baseline 的标准重构全部输出。

1. 细化紧预算扫描区间
    - 根据当前 `full_gpu` 与 `kivi_4bit_residual32` 的实际内存占用，缩小预算搜索范围，并在 profile 可行性边界附近增加更密集的预算点。
    - 先确认预算变化能够使候选 profile 的可行集合发生变化，再扩展到完整 baseline 矩阵。
    - 对每个预算点记录可行 profile、被预算过滤的 profile、最终选择结果和回退原因，避免只通过最终 TTFT 反推选择过程。

2. 验证 profile 选择是否由预算真正触发
    - 分开记录策略层预算过滤与 backend 实际预算命中，保留 `policy_budget_filter_rate` 和 `budget_hit_rate` 的不同语义。
    - 增加选择前后的 projected memory、全局 resident、候选 profile 内存需求和预算余量，确认 profile 改变来自预算约束，而不是 runtime 切换、默认回退或候选缺失。
    - 对未触发 profile 切换的预算点给出明确原因，例如所有候选均可行、仅 exact 可行、候选未进入选择器或选择结果被后端覆盖。

3. 优先保留能够解释预算边界的结果
    - 当前诊断实验可以继续使用通用 summary，但不应将其解释为正式 `baseline_quality` 或 `baseline_session`。
    - 汇总结果至少应保留预算、最终 profile、action distribution、KV 内存、全局 resident、策略过滤、backend 预算命中以及回退原因。
    - 不适用字段保持空值，避免使用 `fillna(0)` 将“未发生”“不适用”和“缺失记录”混为一类。

4. 排除 runtime 噪声对预算结论的干扰
    - 将 cold start、profile switch、worker restart 和 `profile_runtime_released` 单独标注，不把 runtime 生命周期事件解释为预算 eviction。
    - 比较 profile 时同时保留端到端 TTFT 和 warm steady-state TTFT。当前量化 profile 的极高 TTFT 只能作为运行现象，不能直接证明紧预算选择有效。

5. 对预算事件和 resident 账本增加最小校验
    - `budget_hit` 只表示 backend 确实因预算产生 victim 或执行预算处置；fixture 原值单独保存为 `source_budget_hit`。
    - 根据 `event_reason` 和 `budget_resolution` 区分预算 eviction、runtime release 和其他释放事件。
    - 校验 global resident 非负、与各 session resident 基本一致，并确认预算处置后不超过预算。该校验用于保证找到的预算边界不是状态账本错误造成的假象。

6. 找到有效紧预算后再完善正式 baseline 产物
    - 先以“至少两个 profile 在相邻预算点发生稳定、可复现的选择变化”为紧预算搜索成功标准。
    - 成功定位预算区间后，再补齐五条 baseline、统一请求集合、矩阵完整性 gate，以及 `baseline_quality` 和 `baseline_session` 两套正式 schema。
    - 在紧预算尚未触发 profile 分化前，不宜优先投入完整正式表重构，也不能将当前 diagnostic-only 数值用于论文结论或与 TailGuard、Oracle 横向比较。
